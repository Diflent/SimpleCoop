Мультиплеер Ostranauts


Общая архитектура

Host запускает игру + мод → становится сервером.
Client подключается по IP (Hamachi/Radmin VPN) + порт.
Хост симулирует весь мир.
Клиент отправляет **только команды/действия** (ввод, клики, приказы).
Хост применяет команды, симулирует и периодически отправляет состояние (snapshot + deltas).
Нет лобби, нет списка серверов — только прямое подключение по IP:порт

План реализации

3. Разобрать игру декомпилятором

Этап 1. Базовая сеть + подключение
1. На хосте: кнопка “Создать сервер” (слушает порт, например 7777).
2. На клиенте: поле ввода IP + «Подключиться».
3. Handshake (версия мода, проверка совместимости сохранений).
4. Отправка/получение простых сообщений (ping, disconnect).
5. Обработка разрыва соединения и реконнекта.
6. UI-индикатор: «Хост / Клиент / Не подключено».

Этап 2. Синхронизация критического состояния (Гребаный Ад)
Приоритет того, что нужно синхронизировать в первую очередь:


| Приоритет | Что синхронизировать | Как |
| :--- | :--- | :--- |
| Высокий | Позиция/ориентация корабля, скорость | Snapshot + prediction |
| Высокий | Позиции и состояние экипажа (позиции, потребности, задачи) | Периодический snapshot + команды |
| Высокий | Предметы в инвентарях и на корабле | ID + изменения (add/remove/move) |
| Средний | Атмосфера, давление, температура, утечки | Редко (раз в 0.5–1 сек) или по событиям |
| Средний | Время игры / скорость времени | Host управляет, клиент только отображает |
| Низкий | UI, камера, выделения | Локально у каждого игрока |
| Очень низкий | Полная физика частиц/огня | Только на хосте, клиент получает результат |


Реализация:
- Команды от клиента → хост (PlayerAction: клик, приказ экипажу, использование предмета и т.д.).
- Snapshot от хоста → клиент (раз в 100–200 мс полное/частичное состояние важных объектов).
- Delta (только изменения) для экономии трафика.
- При больших расхождениях — hard resync (полная пересылка состояния).

 
Этап 3. Управление и ввод
1. Перехватывать ввод игрока (Harmony-патчи на обработчики кликов, горячих клавиш, UI-кнопок).
2. Если клиент — отправлять действие на хост вместо локального выполнения.
3. Хост выполняет действие и рассылает результат.
4. Разделить управление:
Определиться
   - Оба игрока могут управлять одним и тем же экипажем (проще).
   - Или назначить «своего» персонажа каждому (сложнее, но интереснее). 

Этап 4. Сохранения и загрузка
1. Хост сохраняет мир.
2. При подключении клиент получает полный snapshot текущего состояния (или файл сохранения + дельты).
3. Обработка late-join (подключение уже в запущенную игру).

Этап 5. Полировка
- Компрессия пакетов.
- Prediction + reconciliation (клиент предугадывает движение и корректирует).
- Логирование рассинхрона.
- Защита от читов на минимальном уровне (хост проверяет разумность команд).
- Обработка паузы, ускорения времени, меню.

Возможные, желаемые расширение функционала

1. Больше игроков (3–4) — нужна очередь команд и более жёсткий контроль bandwidth.
2. Назначение ролей (капитан / инженер / медик) — разные права на действия.
3. Shared inventory / shared money.
4. Отдельные камеры и точки обзора без принудительной синхронизации вида.
5. Режим «наблюдатель.
6. Детерминированная симуляция (если удастся заставить игру быть полностью детерминированной — можно перейти на lockstep, но это крайне сложно).
7. Синхронизация модов  (проверка, что у всех одинаковый набор JSON/C# модов). *очень далёкая перспектива
